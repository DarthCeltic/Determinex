## Non-Negotiable Rules

These rules are the lock factory's safety rails.

1. Official ProgramBench eval JSON is score truth.
2. A patch is kept only when passed count increases and runnable total stays
   stable.
3. Ties and regressions are reverted immediately.
4. No fixture or test edits unless upstream binary proves the fixture is wrong.
5. No `full_sweep_iterate.py` for production progress.
6. No broad full-file rewrites over working overrides.
7. No `locked/*` writes unless the tool has a verified official 100/100 artifact.
8. Every accepted patch must produce:
   - gate result
   - eval JSON
   - accepted registry row
   - lesson
   - refreshed board
   - refreshed RAG, when cost is acceptable

## The Core Factory Loop

Use this loop for every tool.

1. **Refresh accounting**
   - Run `scripts/pb_score_audit.py`.
   - Run `scripts/pb_factory_dispatch.py --top N --dry-run`.
   - Confirm the board points to the best reproducible eval, not merely the
     latest artifact.

2. **Refresh failure inventory**
   - Run `scripts/pb_cluster_from_eval.py` against the board-cited best eval.
   - Read the generated `.official_cluster_report.json` and `.md`.
   - If a cluster is too broad, split it manually into semantic sub-buckets
     before patching.

3. **Classify the work**
   - `recovery`: current override does not reproduce best-known score.
   - `model-worker`: tiny additive/localized exactness fix.
   - `hand-specialist`: parser, TUI, table renderer, or algorithmic cluster.
   - `upstream-oracle`: expected behavior is ambiguous or byte-exact.
   - `lock-archive`: verified 100 but archive structure is incomplete.

4. **Make one patch**
   - Only one cluster.
   - Smallest possible code change.
   - Prefer additive exactness before state-machine changes.

5. **Gate**
   - Pack candidate.
   - Run `pb_candidate_gate.py`.
   - Accept only improvement with stable runnable count.
   - Revert otherwise.

6. **Register**
   - Run `pb_apply_gate_decision.py --refresh-board --refresh-rag` on accepts.
   - Stop after one accepted gate so a human/Codex can review and commit.

## Product Correctness Roadmap Beyond ProgramBench

ProgramBench 200/200 is the proof-of-factory milestone, not the universal
"no bugs ever" milestone. It proves that Determinex can convert a large real-world
tool surface into compiler/test-verified source, failure rows, and corrected
implementations. That is the right training signal for an IDE, but the product
claim must stay defensible:

- For domains represented in the corpus, Determinex should generate from verified
  patterns instead of averaged internet code.
- For adjacent domains, Determinex should generalize from verified patterns and
  then run the compiler/test oracle before accepting the result.
- For novel domains, Determinex must add a domain oracle before claiming
  correctness. Compiler pass is necessary, not sufficient.

### Vibe-Coder Intake

The target user should be able to describe an idea in plain language without
knowing the language, architecture, flags, or edge cases. The IDE must translate
that into:

1. intent classification,
2. one or two clarifying questions only when a real branch point exists,
3. language/runtime recommendation with a reason,
4. retrieved verified examples from the closest corpus neighborhoods,
5. generated implementation,
6. compile/test gate,
7. retry with exact failure injection until accepted or escalated.

Required work:

- Build an intent router that maps plain-language ideas to corpus neighborhoods
  such as CLI parser, file watcher, text transformer, binary reader, network
  client, table renderer, TUI, config loader, and data converter.
- Add a "why this stack" explanation artifact to each generation so a user can
  see why Rust, Go, Python, C, or another language was selected.
- Add first-run project templates backed by verified corpus examples, not
  generic boilerplate.

### Legacy Language Expansion

Base-model pretraining may know COBOL, Fortran, Ada, PL/SQL, RPG, MUMPS, and
similar languages, but Determinex only earns the "compiler-verified" claim where
we have an oracle and corpus rows. Legacy support must be sharpened the same
way as Rust/Go/C:

- COBOL: GnuCOBOL compile/run harness, JCL-style batch fixtures, fixed-width
  file processing, report generation, transaction-style examples.
- Fortran: `gfortran` harness, numerical kernels, file formats, scientific
  utilities, precision/regression tests.
- Ada: GNAT harness, package/spec/body examples, strong typing/error handling.
- SQL/PLSQL: dialect-specific containers, migration fixtures, query-plan and
  result-set oracles.

Each legacy lane needs the same artifacts as ProgramBench: source, compile
script, eval JSON, gate result, verdict corpus rows, and lessons.

### Complex Domain Oracles

Novel ML, distributed systems, and domain-specific business logic need stronger
gates than "it compiles." Add domain oracles by category:

- ML systems: shape checks, gradient checks, numerical tolerance tests,
  deterministic seed replay, small reference implementations, benchmark
  regression limits.
- Distributed systems: deterministic simulation, fault injection, race tests,
  Jepsen-style invariants where practical, model-checking for small state
  spaces, log/replay harnesses.
- Security-sensitive code: fuzzing, sanitizer builds, dependency audit,
  constant-time checks where relevant, malformed-input corpora.
- Finance/medical/legal/business domains: property tests and domain-specific
  oracle functions written with expert-reviewed invariants.

These gates should write verdict corpus rows with the oracle type attached, for
example `compiler+unit`, `compiler+property`, `compiler+fuzz`,
`compiler+simulation`, or `compiler+domain`.

### Retrieval And Fleet Learning

RAG should retrieve both successful implementations and failure/fix rows. The
retriever should prefer verified native source over wrapper code and should
surface why a retrieved example is relevant:

- matching language,
- matching IO pattern,
- matching failure class,
- matching domain oracle,
- matching project shape.

Fleet learning should remain opt-in and local-first through Vanguard. New user
work can enter the training queue only after:

1. user consent,
2. local sanitization/redaction policy,
3. compiler/test/domain gate,
4. deduplication,
5. provenance label,
6. replayable artifact path.

### Defensible Claim

The public claim after ProgramBench 200/200 should be:

> Determinex has a compiler/test-verified corpus of 200 real CLI tools across
> native languages and can generate from verified implementation patterns
> rather than unverified code examples. It reduces first-run bugs in represented
> domains and uses deterministic gates to catch failures before acceptance.

Do not claim:

- "no bugs ever,"
- universal correctness for domains without a domain oracle,
- legacy-language correctness before a compiler-gated legacy corpus exists,
- autonomous fleet learning without opt-in provenance and replayable gates.

## Sunday 200-Tool Execution Protocol

The native conversion sprint has two separate goals:

1. move the board score and 100% locks,
2. replace Python wrapper logic with real native source even when a gate cannot
   accept the score change yet.

Do not mix those up. A gate-rejected native implementation can still be useful
training corpus material, but it must be labeled as rejected and must not
replace the official best board row unless the gate accepts it.

### Lane Width

Default to two concurrent eval lanes. Increase to three only after checking that
Docker containers are not paused, memory is stable, and cargo/go builds are not
thrashing. Avoid four or more lanes on the workstation; the wall-clock win is
usually lost to container contention and failed builds.

### Queue Discipline

Use `scripts/pb_native_eval_queue.py` as the source of truth for packed native
candidates:

```powershell
python scripts/pb_native_eval_queue.py --top 40
python scripts/pb_native_eval_queue.py --launch 2
```

The queue snapshot is written to
`logs/programbench_factory/NATIVE_EVAL_QUEUE.json` and classifies packed native
run roots as:

- `queued`: packed, not evaluated yet,
- `evaluated`: eval JSON exists, needs gate,
- `gated:accept`: gate accepted and can be applied/refreshed,
- `gated:reject`: keep as rejected corpus evidence, then triage separately.

Before exporting a candidate to a local or Hetzner eval lane, run the native
source guard:

```powershell
python scripts/pb_native_source_guard.py <override-or-source-path> --slug <slug>
```

The rule is:

- If upstream is Python (`source_language=python` or `keep-python`), Python is
  the correct implementation language and must be preserved.
- If upstream is Go/Rust/C/C++, the candidate must include real native source
  such as `go.mod`, `Cargo.toml`, `main.c`, or `main.cpp`.
- `main.py` is allowed for native tools only as a thin exec wrapper around the
  native binary. Substantive Python logic in a native-language tool is a corpus
  failure, even if tests pass.
- Python orchestration scripts are fine; they are factory tooling, not
  ProgramBench tool implementations.

### Gate Handling

For every completed lane:

1. run `pb_candidate_gate.py` against the current board baseline,
2. apply only `accept` decisions to the board,
3. archive only real 100% locks,
4. ingest verdict rows for rejected native runs only as rejected evidence,
5. record the dominant failure class before launching a targeted retry.

Never patch tests to preserve wrapper-specific behavior. If a fixture appears
wrong, prove it with an upstream/reference binary first and document the exact
oracle mismatch.

### Work Tracks

Run these tracks in parallel:

- Eval grind: keep two to three queued native lanes running until all packed
  candidates have eval JSON.
- Gate/apply: process completed lanes immediately so the board stays current.
- Rejected-native triage: prioritize high-score rejects above 95%, then 90%+,
  then raw-gain rejects over +250 passed.
- Missing-source extraction: build a list of board tools without extracted
  upstream source and recover them from HuggingFace cache or upstream Git.
- Board hygiene: resolve the current 201-row board anomaly before any public
  200/200 claim.

The end-of-day target is full coverage status for every tool: locked, accepted
native, rejected native with failure class, queued/evaluating, or missing-source
with extraction plan.
