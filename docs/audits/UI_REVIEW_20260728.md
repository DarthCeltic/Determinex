# Determinex IDE — UI review against industry standards

**Date:** 2026-07-28
**Question asked:** how to make the UI better for the user, at the standard expected of a
top-tier free/open-source developer tool.
**Method:** measured, not guessed. A Playwright pass drove the real app at 1440×900, opened all
nine rail groups, and recorded computed font sizes, hit-target sizes, accessible names and
overflow for every visible element. Numbers below are from that run. Where a claim is inferred
from reading the code rather than measured, it says so.

**Comparables used as the bar:** VS Code, Zed, Linear, Raycast, Warp — plus WCAG 2.2 AA, which
is the floor an open-source tool is expected to meet if it wants institutional adoption.

## 1. Type size is the single biggest problem — fix this before anything else

VS Code's default UI font is 13px and its own accessibility guidance treats 11px as a floor.
Determinex's *modal* size is 9px, with 121 nodes at 7px and 10 at 6px. 6px text is not small
styling; it is unreadable for a large share of users and effectively invisible on a 4K display
at default scaling.

This is not a taste question, and it is the thing that will most shape a first impression: a
tool whose labels cannot be read reads as unfinished regardless of how good the engine is.

**What to do**

Introduce a type scale and use it everywhere. Nothing below 11px ships.

```css
--dtx-text-xs:  11px;  /* metadata, badges, timestamps — the current 7-9px tier */
--dtx-text-sm:  12px;  /* secondary labels, descriptions */
--dtx-text-base:13px;  /* body, list rows, panel content — the workhorse */
--dtx-text-lg:  15px;  /* panel titles */
--dtx-text-xl:  20px;  /* screen titles — replaces the 24/30px jump */
```

Today the app leaps from a 10px body to a 24–30px display size with almost nothing between: 95
nodes at 11px, 10 each at 12/13/14px. That missing middle is why headings feel shouty and
everything else feels like fine print. Note the layout already survives more text — the drawer,
rail and panels all wrap or scroll — so this is mostly a token substitution, not a re-layout.

Add a **UI density setting** (Comfortable / Compact) rather than hard-coding one choice, the way
VS Code and Linear both do. Compact can keep something close to today's 11px floor for users on
small screens who want it; Comfortable at 13px becomes the default.

**Also add app-level zoom.** `Ctrl/Cmd +` / `-` is muscle memory in every editor and is a
one-line CSS-variable multiplier. It is the cheapest accessibility win available here.

## 2. Hit targets and accessible names

8 interactive elements per screen are **under 24px** in at least one dimension. WCAG 2.2 AA
(2.5.8 Target Size Minimum) sets 24×24 CSS px as the floor. 5 buttons per screen have **no
accessible name at all** — an icon with a `title` attribute is a tooltip, not a name, so a
screen reader announces "button" and a keyboard user gets no hint.

**What to do**

- Minimum 24×24 for every control; pad the icon rather than growing the glyph.
- `aria-label` on every icon-only button. The rail buttons already pair an icon with a text
  label, which is the right pattern — it is the panel-header icon buttons (close, move-to-dock,
  refresh, reveal, clear) that are bare.
- Keep the `title` too: tooltip and accessible name serve different users.

## 3. First run puts two full-screen modals in the way

Measured behaviour: on a fresh profile the setup wizard mounts `fixed inset-0 z-50`, and after
it the workspace-onboarding sheet does the same — and that sheet renders a full-bleed spinner
*before* it renders its own dismiss button. Nothing behind either is clickable until both are
dealt with. This cost real time during this very audit: the first two attempts at driving the
app failed because clicks were landing on an invisible overlay.

The setup wizard earns its modal — it configures a network policy and pulls a model, and that is
a genuine gate. The onboarding sheet does not: it reports a workspace scan.

**What to do**

- Demote workspace onboarding from a blocking modal to a **dismissible banner or side sheet**.
  A scan result is information, not a decision.
- Never render a full-screen blocker whose only content is a spinner. Put progress inline where
  the result will appear.
- Give both a visible **Escape-to-close** and a focus trap while open (neither is currently
  wired, from reading the code).

---

## 4. Empty states should teach, not just report

Several panels correctly say they are empty — "No sessions yet", "No pending changes to review",
"No live output loaded". That honesty is a genuine strength of this codebase and should be kept.
But the current versions stop at the fact.

The best-in-class pattern (Linear, Raycast) is: **state + one action + one sentence of why**.
OutputPanel already does this well — *"No hive sessions yet. Run a build from Work and its
output appears here."* That is the template; propagate it. Every empty state should name the
button that fills it.

---

## 5. Keyboard-first is half-built

There is a command palette (`showPalette` state exists). What is missing, from reading the code:
a documented shortcut for it, a visible shortcut hint in the UI, Escape handling on the drawer,
and any focus-visible styling.

For a developer tool this is table stakes, and it is also the cheapest way to make the app feel
fast to an expert:

- `Ctrl/Cmd+K` — command palette, hinted in the UI, listing every one of the 36 surfaces by name.
- `Ctrl/Cmd+1..9` — the nine rail groups.
- `Escape` — close the drawer, close the top modal.
- A `:focus-visible` ring on every control. Currently focus is effectively invisible, so
  keyboard navigation cannot be followed.
- A discoverable shortcut sheet (`?`).

## 6. Panel resizing — CORRECTED: this item was wrong

This originally read *"Zone 2 and Zone 3 are not resizable — only Zone 1 is."*
**Both halves of that are false**, and I found out by measuring instead of reading.

Dragging Zone 1's handle 180px in the running app:

```
before:  rail 72px | Zone 1 460px | Zone 2 844px
after:   rail 72px | Zone 1 640px | Zone 2 664px
```

Zone 2 is `flex-1`, so it already resizes with Zone 1's handle — there is nothing
to add. And there is no Zone 3: the shell has exactly three columns, one of which
is the fixed 72px rail (correctly fixed). What looks like a third panel is an
internal two-column grid *inside* Zone 2.

The one real gap from this item stands: **panel arrangement is not persisted as a
named layout.** Widths are, per surface. Named, restorable workspace layouts are a
genuine feature request, not mechanical cleanup, and are listed as such.

## 7. Colour, contrast and motion

Not measured — contrast ratios need a colour-math pass I did not run, so this is a read of the
code, flagged as such.

The palette is a dark theme with per-surface accent colours and heavy use of `text-gray-600` /
`text-gray-700` on near-black backgrounds. `text-gray-600` (#4b5563) on `#0d1117` is
approximately 3.4:1 — **below the 4.5:1 WCAG AA floor for body text**, and it is used for
descriptions and hints, not decoration. Worth an actual measured pass; my expectation is that
the secondary text tier fails AA fairly broadly.

Also: accent colour is currently the *only* channel distinguishing several states. Add a second
channel (icon shape, or a label) so the UI does not depend on colour discrimination alone.

`prefers-reduced-motion` is not honoured anywhere I can find. The shell animates panel entry
with springs; that should collapse to an instant transition when the OS asks.

| # | Change | Impact | Effort |

| 1 | Type scale, 11px floor, 13px body + density setting + zoom | Transforms first impression | M |

| 5 | Contrast pass to AA on the secondary text tier | Accessibility + readability | M |
| 6 | Empty states get an action + a reason, on the OutputPanel model | Teaches instead of reporting | S |
| 7 | ~~Resize Zones 2/3~~ — already works, measured. Named saved layouts remain a real feature request | Power-user retention | M |
| 8 | `prefers-reduced-motion` | Correctness, small | S |

Items 2, 3, 6 and 8 are each an afternoon and would be visible immediately. Item 1 is the one
that changes how the product is perceived.

## What is already good, and should not be traded away

- **Honest empty states and honest labels.** Panels say when they have nothing, and the codebase
  has a strong habit of refusing to imply a capability it does not have. That is rarer than it
  should be and is worth protecting.
- **The nine-group rail with a naming drawer.** 36 surfaces are reachable and every one explains
  what it is and what it does *before* you spend screen space on it. Measured: every group opens,
  every group has members.
- **No horizontal page scroll** at 1280 / 1440 / 1920.
- **Per-surface persisted panel widths.** The right instinct — remember the user's choice, per
  context.

---

## Method notes and limits

- Measurements come from `next dev` in a browser, so the Tauri IPC layer is absent and
  backend-dependent panels render their "needs the desktop runtime" state. Layout, navigation,
  type scale and hit targets are all still real; per-panel *content* density in the desktop app
  is not covered here.
- Contrast (§7) is inferred from the code, not measured.
- The five Playwright specs added this session (`playwright-tests/shell.spec.ts`) pin the
  structural half of this — nine groups reachable, drawer names its members, no clipped content,
  no horizontal overflow — so those cannot regress silently.
