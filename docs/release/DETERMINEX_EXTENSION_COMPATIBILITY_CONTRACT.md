# Determinex Extension Compatibility Contract

Status: contract defined; runtime evidence generated by
[`scripts/release/extension_compat_packet.py`](../../scripts/release/extension_compat_packet.py).

This contract defines the minimum bar for claiming VS Code/Open VSX compatibility. It does not claim that extension runtime compatibility is complete.

**Two directions, and this document covers both.** Everything below the "Supported Package Intake"
heading is about extensions coming *into* Determinex. The `extension_compat` release gate, however,
lists `frontend/vscode-extension` as its evidence — our own extension going *out* to VS Code and
Open VSX. That direction was never written down here, which meant the gate pointed at a contract
that did not describe the thing being gated. The "Published Extension" section below closes that.

## Supported Package Intake

- Accept `.vsix` packages from local disk after checksum recording.
- Accept Open VSX metadata only after source URL, publisher, version, and license fields are captured.
- Reject packages that request unsupported host APIs unless an explicit compatibility shim exists.
- Store installed extension state under the Determinex user profile, not inside a project checkout.

## Trust Boundary

- Extension install is a user-authorized action.
- Activation runs inside the Determinex extension sandbox.
- Extension code must not receive raw API keys, model secrets, payment identifiers, or unrestricted filesystem access.
- Workspace access must be scoped to the active project root and surfaced in the UI before activation.

## Published Extension (the outgoing direction)

Identity: **`darthceltic.determinex`**, licensed AGPL-3.0-or-later, `engines.vscode ^1.85.0`.

The extension implements no logic of its own. Every command shells out to the one governed backend
entry point, `scripts/ide/determinex_backend_cli.py`, with a **fixed argv** — no shell, no string
interpolation into the command — and the manifest declares no `capabilities`.

It contributes exactly four commands:

| Command | Title |
| --- | --- |
| `determinex.buildFromIdea` | Determinex: Build From Idea (verified) |
| `determinex.previewIdeaOracle` | Determinex: Preview the Sound Oracle for an Idea |
| `determinex.repairDiagnose` | Determinex: Diagnose This Repo (blame + slop) |
| `determinex.governanceStatus` | Determinex: No-Overclaim Governance Status |

`activationEvents` is deliberately empty: VS Code ≥ 1.74 synthesises implicit `onCommand:` events
from `contributes.commands`, so the extension activates when a command is invoked and not before.
That is a runtime assumption, not a manifest fact, so `activation_event_smoke_passed` is established
by running a suite inside a **real extension host** (`@vscode/test-electron`) which observes the
inactive→active transition — commands are absent from the command registry until activation, and
present after it.

## Runtime Compatibility Bar

The `extension_compat` release gate may pass only after a packet records
`schema_version: determinex-extension-compat-runtime-evidence-v1` together with:

- `extension_api_contract_defined: true`
- `vsix_import_smoke_passed: true`
- `open_vsx_metadata_parsed: true`
- `sandbox_permissions_enforced: true`
- `activation_event_smoke_passed: true`
- `authority_granted: false`

## Non-Claims

- This contract does not claim complete VS Code API parity.
- This contract does not claim marketplace publication.
- This contract does not bypass installer, trust, clean-host, or benchmark release gates.
