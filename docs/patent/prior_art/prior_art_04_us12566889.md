## Primary Mechanism Disclosed (Summary of Claims 1–3)

A system and method for LLM-agnostic data anonymization where user documents are intercepted at upload, parsed for confidential information, and obfuscated before transmission to an LLM API. After the LLM returns a response, the obfuscated identifiers are deobfuscated in the response before presentation to the user.

**Obfuscation methods:** encryption with a private key, a replacement list, or a hashing-and-replacement dictionary.

**Confidential information detection:** machine-learning classifier or context-based search against a predefined word list.

The claims are **document / natural-language oriented** — they target PII (personally identifiable information) in generic text documents.

## What This Reference Does NOT Disclose

1. **No AST-level code parsing.** Claims are drafted for general documents and PII, not for source code syntax trees. No disclosure of language-specific AST traversal (Python `ast.NodeVisitor`), identifier categorization by syntactic role (function names vs. class names vs. variables), or cross-file scope tracking (e.g., star-import resolution).

2. **No compilability requirement.** The Acronis patent obfuscates text documents — there is no requirement that the obfuscated output remain syntactically valid, compilable code. Project Cloak's central claim is that obfuscated code is **still compilable** by a real compiler (e.g., `python -m py_compile`) in an isolated worktree, enabling the compile-gate pipeline.

3. **No reverse-mapping of LLM output as a code patch.** The Acronis patent deobfuscates API responses for human display. Project Cloak deobfuscates LLM-generated **code patches** for application to a real codebase — a structurally different output type with different validation requirements (patch syntax, diff application, compile-gate).

4. **No compiler-verified patch restoration loop.** No iterative compile-fail → re-obfuscate errors → re-inject → retry mechanism.

5. **No semantic key generation.** No local word-splitting approach to providing functional context without exposing real identifiers. The Acronis patent uses either encryption (one-way for the recipient AI) or a replacement dictionary (no functional description of what the replaced identifier means).

6. **No Context Paradox Pattern.** No separation between discovery (unobfuscated) and transmission (obfuscated) phases.

7. **No MLP encoder/decoder latent bridge.** The patent is entirely about prompt-level text substitution, not model internal representations.

8. **No L2 Egress Filter.** No API gateway enforcement blocking cloud calls when obfuscation is not confirmed active.

9. **No AuditLogger / zero-leakage audit artifact.** No post-run cryptographic verification that no real identifiers appeared in any API request.

## Closest-Claim Overlap Assessment

**Risk area (for attorney review):** The broadest concept — "obfuscate identifiers before sending to cloud LLM, deobfuscate the response before use" — is disclosed. A broad claim drafted as simply "a method for obfuscating code identifiers before LLM API transmission" would likely face 102 rejection based on this patent.

**How to differentiate (attorney to validate):**
- Claims must recite **AST-level identifier classification** (not string/word-list matching)
- Claims must recite **compilability preservation** (obfuscated code passes compile check)
- Claims must recite **code patch output** (not general text document response)
- Claims must recite the **semantic key mechanism** (local word-splitting + syntactic category annotation, never transmitted)
- Claims must recite the **Context Paradox Pattern** (discovery on real text, transmission on obfuscated text)
- The compile-gate integration (obfuscated code compiled in isolated worktree) is entirely absent from Acronis

The combination of (1) AST-awareness, (2) compilation validity, (3) patch output, (4) semantic key, and (5) compile-gate is **not anticipated** by this patent even under the broadest reading of its claims.
